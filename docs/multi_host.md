# Бонус: шард на іншому комп'ютері

Мета: додати до кластера четвертий воркер Citus, що працює на ноутбуці іншого учасника команди,
і перенести на нього частину шардів. Кластер при цьому працює далі, і дані не губляться.

> Перевірено лише в межах одного комп'ютера (див. «Що перевірено»). Перед захистом прогоніть ці кроки
> на двох ноутбуках у тій самій мережі Wi-Fi.

## Що потрібно

- Обидва комп'ютери в одній локальній мережі (бажано домашня мережа або точка доступу з телефону: університетська
  Wi-Fi часто блокує з'єднання між клієнтами).
- Docker на обох.
- IP другого комп'ютера (macOS: `ipconfig getifaddr en0`, Windows: `ipconfig`).

## Кроки

**Комп'ютер Б (учасник команди):**
```bash
git clone <репозиторій> && cd InfoSpaceMission
docker compose -f docker-compose.remote-worker.yml up -d   # воркер Citus на порту 5433
```
Порт 5433 відкритий у локальну мережу, вхід лише за паролем. macOS може запитати дозвіл на вхідні з'єднання —
дозвольте. Після захисту: `docker compose -f docker-compose.remote-worker.yml down -v`.

**Комп'ютер А (основний кластер):**
```bash
# перевірка, що воркер Б досяжний (має відповісти "accepting connections")
docker compose exec citus-coordinator pg_isready -h <IP_Б> -p 5433

# перезапустити застосунок із додатковим воркером (кома на початку — обов'язкова)
REMOTE_WORKERS=,<IP_Б>:5433 docker compose up -d app
```
На старті застосунок виконає `citus_add_node('<IP_Б>', 5433)`. Пароль для з'єднання координатор бере з
`pg_dist_authinfo`, а застосунок записує його туди сам.

**У веб-застосунку:**
1. «Відмовостійкість» → у таблиці вузлів з'явився `<IP_Б>:5433`, стан «працює», шардів 0.
2. «Шардінг» → **«Ребалансувати шарди»** (`citus_rebalance_start(shard_transfer_mode := 'block_writes')`).
   Citus переносить частину з 12 шардів на новий вузол, щоб на кожному було по 3. Натискаючи «Оновити», видно,
   як шарди переїжджають. Під час перенесення запис у конкретний шард короткочасно блокується, а генератор
   чекає й повторює пачку (див. load_testing.md, розділ 6).
3. «Шардінг» → розподіл рядків уже по 4 вузлах; map-reduce звертається напряму і до віддаленого вузла.
4. Можна повторити замір швидкості запису («Навантаження» → «Заміри») і порівняти з 3 локальними воркерами.

Стан ребалансування з консолі:
```bash
docker compose exec citus-coordinator psql -U space -c "SELECT * FROM citus_rebalance_status()"
```

## Як прибрати віддалений воркер

Спочатку перенести шарди назад, потім видалити вузол:
```bash
docker compose exec citus-coordinator psql -U space -c \
  "SELECT citus_drain_node('<IP_Б>', 5433, shard_transfer_mode := 'block_writes')"
docker compose exec citus-coordinator psql -U space -c "SELECT citus_remove_node('<IP_Б>', 5433)"
docker compose up -d app        # без REMOTE_WORKERS
```

## Можливі проблеми

| Симптом | Причина / що робити |
|---|---|
| `pg_isready` не відповідає | Брандмауер на Б або мережа ізолює клієнтів — спробуйте точку доступу з телефону |
| `password authentication failed` | На Б змінено `POSTGRES_PASSWORD` — він має збігатися з паролем у `DATABASE_URL` (space) |
| Ребалансування стоїть | Подивіться `citus_rebalance_status()`; перенесення шарда копіює дані по Wi-Fi, на великих обсягах це хвилини |
| Відключили Б, не прибравши вузол | Шарди на Б недоступні, запис пригальмовує (дані на Б не губляться); увімкніть Б знову або виконайте `citus_drain_node` |

## Що перевірено

- На одному комп'ютері: запуск кластера з 3 воркерами з цими налаштуваннями (запис `pg_dist_authinfo` на старті)
  і кнопка «Ребалансувати шарди» (на рівномірному кластері відповідає «Шарди вже розподілені рівномірно»).
- **Не перевірено:** воркер на іншому комп'ютері й перенесення шардів на нього. Прогоніть ці кроки на двох
  ноутбуках перед захистом.
